# 首次 HCU 实机验证记录（2026-11-17）

结论：**基础实机运行与请求一致性验证完成；性能测量的完整验收尚未通过。** 原定矩阵、独立工具对照和 CPU 对照全部运行完成，但没有 exporter，且仍存在超出单组重复波动的细小延迟偏移，不能宣称性能数据已完成校准。

## 范围和身份

- 私有仓库 `dddddddxl/aiperf-hcu`，开发分支 `codex/hcu-adaptation-v1`；未公开或合并 main。
- 适配包 `0.1.0a2`，固定 AIPerf v0.13.0 / `794f8bb75f8582f22e412d7e650fc71ca2a3d21a`；核心引擎算法未修改。
- 用户明确授权单张物理卡，并要求发现其他任务在该卡分配显存立即停止本次工作。只停止本次自有容器，不操作其他任务。
- Qwen3-4B BF16、BW1100 单卡、TP1，使用本地权重和 tokenizer，没有下载大模型或调用付费模型 API。
- 服务镜像和资源隔离、cookbook 配置差异见 [实测启动说明](SGLANG-QWEN3-BW1100.md)。
- 全程流式，server usage 计数，固定输出 128；禁用 radix cache。服务端与客户端分离 Python 环境，未修改节点驱动、Torch 或 DTK。
- 每轮故障上限经用户批准从 600 增加到 900 秒；请求数和并发没有减少或增加。

## 原定矩阵

每点正式 128 请求 × 3 轮。固定长度点每轮预热 16 次；Poisson 点按原协议不预热，输入目标 512±128，最大并发 8。原始逐请求记录区分 warmup/profiling，最终计数不包含预热。

六个场景共 **18 轮、2,304 个正式请求全部通过**。每条正式请求都有服务端 usage，输出最小值/最大值均为 128；实际最大在途数没有超过配置上限。没有触发 900 秒故障上限。

下表均为三轮的均值；吞吐的 ± 是三轮均值的样本标准差，不是置信区间。

| 场景 | TTFT 均值 ms | ITL 均值 ms | 请求延迟均值 s | 输出吞吐 token/s |
|---|---:|---:|---:|---:|
| 固定长度，并发 1 | 105.60 | 33.34 | 4.340 | 29.48 ± 0.09 |
| 固定长度，并发 4 | 192.10 | 36.06 | 4.772 | 107.20 ± 0.04 |
| 固定长度，并发 8 | 206.49 | 35.98 | 4.775 | 214.19 ± 0.89 |
| Poisson 目标 1 req/s | 156.37 | 39.54 | 5.178 | 116.79 ± 0.16 |
| Poisson 目标 2 req/s | 166.46 | 40.34 | 5.290 | 148.97 ± 0.13 |
| Poisson 目标 4 req/s | 177.59 | 40.09 | 5.269 | 169.82 ± 0.05 |

固定输入目标 128 经 chat 模板后实际为 136。变长输入实际均值 524.125、样本标准差 131.93、范围 162～826；各轮采用同一随机种子重放同一输入分布，不是三组独立随机语料。所有指标限定到本次资源受限、graph/overlap 关闭的配置。

**Poisson 配置目标不等于实际负载。** 根据正式请求开始时间戳计算 `(N-1)/(最后开始-最早开始)`，三档实际派发速率分别约为 0.940～0.943、1.211、1.387 req/s。配置中同时限制最大并发 8，后两档明显没有达到无约束 Poisson 的目标派发率；不能把这次结果表述成“已承受真实 4 req/s 的开放到达流量”。请求完成吞吐与上述派发速率也不是同一个统计窗口。

原始每轮 p50/p95/p99 保留在机器摘要和原版工件中，没有平均各轮 p99 来冒充整体 p99。矩阵墙钟约 63.24 分钟，包含每次上游进程准备、预热和收尾；它不等于用于吞吐计算的正式请求窗口。

例如 TTFT 的逐轮 p99：固定并发 1 为 110.84～113.44 ms，并发 8 为 212.37～217.37 ms；Poisson 目标 4 req/s 为 328.62～345.53 ms。这是各轮分位数的范围，不是合并请求后的整体 p99。

## 跨工具与干扰检查

- EvalScope 固定 1.13.0，单独 Python 3.11 环境；复用 AIPerf 真实请求对象，不另造随机提示词。
- 请求预检通过 128 条：仅补充显式温度 0.6，与服务端配置默认值一致；预检生成请求数为零。
- 实际三轮均通过原生数据库核对：每轮 128 条成功、136 输入/128 输出、全流式；发送的完整请求集合与冻结请求完全匹配（含上述显式温度差异），而非只核对请求数。
- AIPerf ITL 与 EvalScope TPOT 更接近；各自原生 ITL 和延迟结束边界并非完全相同，不能单凭同名指标判断谁更准确。
- 两工具原生预热交接方式不同：AIPerf 等本轮预热结束再开始正式阶段；EvalScope 闭环按并发槽位交接，尾部预热可能与正式请求短暂重叠。两者正式计数都不包含 16 次预热，但不能把调度时间线描述为完全一样。
- 客户端 4→8 CPU 对照已执行三轮，其他负载和服务端配置不变；新增 CPU 集即时空闲率约 96%～100%，但这不等于获得整段时间的 CPU 独占。
- **没有可用 hcu-exporter**：四项性能遥测与遥测开关干扰对照未验证。显存保护日志不是性能遥测替代品。

| 并发 8 对照 | 正式请求 | 输出吞吐 token/s，均值±样本标准差 | TTFT 均值 ms | 完整响应均值 s | ITL / TPOT 均值 ms |
|---|---:|---:|---:|---:|---:|
| AIPerf，客户端 4 CPU | 384/384 | 214.19 ± 0.89 | 206.49 | 4.775 | ITL 35.98 |
| EvalScope，客户端 4 CPU | 384/384 | 213.24 ± 0.06 | 213.64 | 4.801 | TPOT 36.12；原生 ITL 36.41 |
| AIPerf，客户端 8 CPU | 384/384 | 213.18 ± 1.01 | 209.70 | 4.800 | ITL 36.14 |

解释与边界：

- 两工具的请求集合、实际输入输出和成功率一致；吞吐数值接近，但这不等于时间测量经过校准。
- EvalScope 与 AIPerf 的 TTFT 均值相差约 **7.14 ms**，大于各自三轮均值的波动范围。已确认预热交接和客户端实现不同，但没有同一条 HTTP/SSE 轨迹的双解析证据，不能将全部偏差武断归因于某个工具。两者完整延迟终点不同可以解释部分端到端差异，**不能用它解释 TTFT 差异**。
- 8 CPU 并没有提高吞吐，两个 AIPerf 组的吞吐范围有重叠，没有观察到“增加 CPU 后明显解除瓶颈”的现象；这不是证明客户端永远不会成为瓶颈。
- 8 CPU 组的 TTFT 仍比 4 CPU 组高约 **3.21 ms**，高于各组内部均值范围。两组按先后顺序运行，没有 4→8→4 回切控制，也缺少温度/功耗/频率关联记录，因此不能证明偏移由 CPU 配额引起，或宣称完全没有测量干扰。
- 不自动增加额外压力点，不为了让数字接近而调整 token 口径或删除某轮结果。下阶段在可用 exporter 和更稳定的 CPU 资源条件下，做配额回切与同轨迹解析核对，再决定能否发布正式性能基准。

合计完成 **3,072 个正式请求**（原矩阵 2,304 + EvalScope 384 + CPU 对照 384），不含预热与冒烟。所有本次 GPU 测试结束后，服务和客户端容器均已停止；显存检查确认本次进程已释放该卡。停止其他任务、重启节点或修改主机全局参数的次数为零。

## 本次发现与修复

1. 容器单卡映射后仍使用物理卡号设置 ROCR 可见性会使运行时无法初始化；改为容器内索引，并先验证实际设备。
2. gfx936 FlashAttention 要求 KV block 大小满足 64 的约束；按 cookbook 设置 page size 64 后启动成功。
3. 首次 10 请求冒烟中，服务端生成 128 token，客户端返回文本重分词得到 127：保留首次“不完整”结果，增加显式 server/client 配置，转发上游原生选项，不修改 token 或时延算法。
4. chat 模板造成输入目标 128 与服务端实际 136 的区别，报告分别保留目标与实测，不把它记成同一个数。
5. 矩阵生成脚本原先写死 600 秒，已改为继承配置并加回归；单并发实测每轮约 630 秒，验证了此次调整的必要性。
6. 手动停止本次服务时，守护读取进程表可能遇到退出竞争；重新核对本次精确容器的状态，正常停止不再误判为存活服务的查询故障。运行中无法可靠查询仍停止本次实验。

- 完整引擎源码 commit 和权重版本；已保存镜像摘要、安装版本、tokenizer 哈希，不补造未知身份。
- 其他模型、量化、卡型、vLLM、多节点、生产容量、回答质量或最优吞吐。
- Qwen3 在输出上限内可能只产生思考内容，没有非推理输出时 TTFO 未测量；不填零。
- 共享节点上的 CPU 核集合限制不等于 CPU 独占，三轮重复不是严格统计认证；不设置自动性能放行阈值。
