# AIPerf HCU：仓库用途与适配进展

更新日期：2026-11-20（最近一次硬件实验：2026-11-18）

## 一、项目是什么

`aiperf-hcu` 是面向海光推理服务的性能评测套件，采用 **上游 AIPerf 压测引擎＋海光适配层** 的方式实现。

它向已经部署好的模型服务发送请求，测量响应延迟、输出吞吐、请求成功情况，并保存可核对、可追溯的实验结果。它不是推理引擎，不会直接加速模型，也不负责自动部署或重启模型服务。

- 项目仓库：[dddddddxl/aiperf-hcu](https://github.com/dddddddxl/aiperf-hcu)，目前为私有仓库。
- 开发分支：`codex/hcu-adaptation-v1`，尚未合并到 `main`。
- 当前适配包版本：`0.1.0a2`。
- 固定上游：AIPerf `v0.13.0`，提交 `794f8bb75f8582f22e412d7e650fc71ca2a3d21a`。
- 当前范围：单节点物理卡上的文本 Chat Completions 服务。

**当前结论：基础压测、单卡四项硬件遥测和遥测开关对照均已跑通。** 结论仅限已测组合；逐样本遥测新鲜度未知，跨工具的延迟偏移仍待解释。

## 二、这个仓库能干什么

### 适用场景

| 场景 | 要回答的问题 |
|---|---|
| 推理框架及适配版本回归 | 更新 SGLang、DTK 或适配代码后，性能是否退化？ |
| 部署参数比较 | 不同并行度、缓存或量化配置下，吞吐和延迟如何变化？ |
| 服务容量评估 | 在可接受的延迟范围内，服务能支撑多少并发和请求？ |
| 固定及变长负载验证 | 固定长度与接近实际业务的变长输入，性能表现有什么不同？ |
| 性能结果交付 | 如何保存运行条件、原始输出和统计口径，让结果能够复验？ |

这些是工具的用途，不代表所有配置组合都已通过海光实测。目前只对本文列出的单卡组合做出了验证。

### 主要入口

| 命令 | 功能 |
|---|---|
| `aiperf-hcu doctor` | 检查依赖、模型接口、本地 tokenizer、可选遥测及输出路径；不发送生成负载 |
| `aiperf-hcu run` | 按配置调用固定版本 AIPerf，串行执行重复实验，保存原始工件 |
| `aiperf-hcu report` | 校验工件哈希并输出中文报告，不改写首次运行结果 |
| `aiperf-hcu compare` | 核对实验条件并比较结果；关键身份未知或条件不匹配时不计算性能提升百分比 |

使用示例：

```bash
aiperf-hcu doctor --config configs/bench.local.yaml --output artifacts/first
aiperf-hcu run --config configs/bench.local.yaml --output artifacts/first
aiperf-hcu report --input artifacts/first
aiperf-hcu compare --baseline artifacts/first --candidate artifacts/second
```

每次运行主要保留：

- `manifest.json`：实验身份、版本、配置摘要和工件哈希。
- `summary.json`：机器可读指标与完整性状态。
- `report.md`：中文报告。
- 每轮上游原始结果、实际命令、进程日志及 `telemetry.jsonl`。

报告区分 TTFT、TTFO、请求延迟、ITL、吞吐、实际输入输出长度和失败情况。无有效非推理输出时，TTFO 标记为未测量；不把各轮 p99 的平均值冒充所有请求的整体 p99。

## 三、已经完成的适配工作

| 方向 | 已完成内容 | 价值与边界 |
|---|---|---|
| 独立环境与版本固定 | 独立 Python 3.11 客户端、固定上游提交与依赖锁、提供 wheel 安装包 | 不修改服务端 Python、Torch、DTK；不修改上游请求调度和指标核心算法 |
| 配置入口 | YAML 配置服务、模型、负载、重复次数、超时、遥测及设备映射 | 不接收任意 shell 命令；凭据通过环境变量引用 |
| 本地 tokenizer | 校验文件哈希，建立本轮专属离线缓存供上游加载 | 兼容固定上游版本的本地 tokenizer 使用方式，不自动下载模型或 tokenizer |
| token 计数口径 | 显式支持 `client` 与 `server`，后者调用上游原生 server usage 计数功能 | 记录口径并纳入比较条件；缺少 usage 不静默回退或填零 |
| 执行保护 | 串行重复、显式故障超时、旧输出目录拒绝覆盖、失败后停止后续轮次 | 失败、中断及计数异常保留工件，不伪装成成功 |
| 海光遥测 | 旁路读取 hcu-exporter，映射功耗、温度、显存、利用率 | 已用真实 exporter v3.0.2 在单卡压测中核对四项指标；不把抓取时间用作设备采样时间 |
| 设备身份关联 | 按节点与 PCI BDF 对应物理设备，保留映射来源 | 不仅凭容器内卡号归属指标；未知和陈旧数据不填零 |
| 中文报告与复验 | 中文说明、报告、机器摘要、原始输出与哈希核验 | 区分运行成功、遥测完整和性能可信，不将三者混为一谈 |
| 自动化验证 | 本地模拟服务、异常场景回归、Linux CPU CI、干净安装验证 | CI 不占 HCU 卡，不自动运行真实模型压测 |
| 单卡部署说明 | 整理实际验证的 SGLang 启动配置及容器设备映射方法 | 说明限定于已测试组合，不承诺通用适配所有模型和卡型 |

遥测参考 exporter 固定提交为 `30cfbc1031957737731725ceddb663bc508d7c96`，对应指标为：

- `hcu_power_usage`：功耗，W。
- `hcu_temp`：温度，℃。
- `hcu_usedmemory_bytes`：显存使用量，bytes。
- `hcu_utilizationrate`：瞬时 CU 利用率，%。

无源时间戳时，新鲜度保留为未知，不用本地采集时间冒充设备采样时间。采集端异常可能产生的零值，也不能直接证明设备健康。

### 遥测是做什么的

遥测就是：**压测时同时记录海光卡的硬件状态，帮助解释性能为什么变化。** AIPerf 测量服务表现，旁路遥测记录设备当时的状态，两者用途不同。

| 服务侧现象 | 关联观察的硬件状态 | 可以提供的排查线索 |
|---|---|---|
| 吞吐上不去 | CU 利用率 | 卡是否持续处于高利用率；低利用率时仍需进一步检查服务调度、CPU、网络等环节 |
| 延迟突然升高 | 温度、功耗变化 | 是否与设备状态变化同时发生 |
| 请求失败或 OOM | 显存使用量 | 是否伴随显存压力；瞬时峰值可能被采样遗漏 |
| 相同配置两次跑分不同 | 四项指标的时间变化 | 两次实验的硬件状态是否一致，为解释波动补充证据 |

**时间上的相关性不是根因证明。** 例如，温度升高与延迟增加同时出现，并不能直接证明发生降频，还需要频率、限频原因或进一步的控制实验。利用率也不能单独证明性能瓶颈所在。

本项目的采集方式是：

1. AIPerf 向模型服务发送请求，测量延迟、吞吐和错误。
2. 独立旁路采集器默认约每 1 秒读取一次 hcu-exporter 的 Prometheus `/metrics`。
3. 按节点与 PCI BDF 映射到服务使用的物理卡，保存指标来源、单位、时间戳和采集失败记录。
4. 将 `telemetry.jsonl` 与同次压测工件一起保存，在报告中展示可用数据与完整性状态。

旁路采集覆盖压测子进程生命周期，包含准备和预热，不等于只覆盖正式测量窗口。秒级采样用于观察硬件状态趋势，不是逐 token 或逐算子的 profiler，也可能遗漏短暂峰值。

遥测只读采集，不调节功耗、不控制风扇、不修改模型服务，也不自动部署或重配节点上的 exporter。

**没有遥测也能完成基础吞吐和延迟压测，只是异常解释和运行条件核对少了一层依据。** 它不应被当作基本请求成功的前提；但本项目首版完整验收包含真实遥测，因此不能在缺失时宣布全部验收完成。

11 月 17 日的基准矩阵未启用 exporter；11 月 18 日另用真实 exporter 做了三对开关实验，共 768 个正式请求。相同并发下，两组平均输出吞吐接近，开启组平均 TTFT 高 0.90 ms；这不能证明遥测开销为零。见[硬件指标、采集周期与配对结果](HCU-TELEMETRY-AB-20261118.md)。

## 四、目前完成了哪些验证

### 1. 软件验证

- 46 项自动化测试通过，零跳过。
- 普通安装与独立干净 wheel 安装均通过测试。
- 回归覆盖流式与非流式响应、错误、超时、断流、计数边界、遥测映射、工件保护和比较条件等。
- 本地模拟测试不能替代真实 HCU 性能验证。

### 2. 单卡实机验证

验证组合：**Qwen3-4B BF16＋SGLang 海光版本＋单张 BW1100，TP1**。采用流式响应和服务端 usage 计数，输出目标为 128 token。具体启动条件见 [SGLang 实测配置](SGLANG-QWEN3-BW1100.md)。

| 验证项目 | 完成情况 |
|---|---|
| 固定长度，并发 1／4／8 | 每点正式 128 请求，重复 3 次；每轮另有 16 次预热 |
| 变长输入，Poisson 目标 1／2／4 req/s | 最大并发 8，每点正式 128 请求，重复 3 次 |
| EvalScope 交叉检查 | 固定 1.13.0，独立环境，并发 8，三轮共 384 个正式请求 |
| 客户端 CPU 配额对照 | AIPerf 客户端从 4 CPU 增至 8 CPU，三轮共 384 个正式请求 |
| 总量 | 3,072 个正式请求通过计数和长度核对，不含预热及冒烟 |
| 工件完整性 | 10 份 manifest、488 个引用工件哈希通过核验，首次失败记录保留 |

原定矩阵共 18 轮、2,304 个正式请求；加上两个对照组后合计 3,072 个。每轮故障上限经授权调整为 900 秒，未触发超时。测试结束后已停止本次服务及客户端并释放测试卡，没有停止其他任务或修改主机驱动、Torch、DTK。

并发 8 的三轮平均观测值：

| 客户端 | 输出吞吐 token/s | TTFT ms |
|---|---:|---:|
| AIPerf，4 CPU | 214.19 | 206.49 |
| EvalScope，4 CPU | 213.24 | 213.64 |
| AIPerf，8 CPU | 213.18 | 209.70 |

这些数字只描述本次固定条件下的观测，**不是 AIPerf 加速模型的证据，也不是工具优劣排名**。

必须同时保留的解释：

- 固定输入目标 128，经过 chat 模板后实际输入为 136；目标长度与实际长度分别记录。
- Poisson 目标 1／2／4 req/s 的实际派发速率约为 0.94／1.21／1.39 req/s。受最大并发与服务处理时间约束，不能宣称已达到持续 4 req/s 的开放负载。
- 两个工具的请求集合、长度和成功率可核对，但延迟统计与预热交接方式并非完全相同。
- TTFT 约 7.14 ms 的跨工具偏移尚未完全归因；4／8 CPU 对照也存在约 3.21 ms 偏移。
- 增加客户端 CPU 未观察到明显吞吐提升，不代表已证明所有负载下客户端都不会成为瓶颈。

完整数据与限制见 [实机验证报告](HCU-VALIDATION-20261117.md) 和 [机器可读摘要](hcu-validation-summary.json)。

### 3. 实测发现并修复的问题

1. **物理卡与容器内索引不同：**调整专用服务的可见设备配置，并核对实际设备身份。
2. **FlashAttention 配置约束：**按实测环境配置 page size 64，解决启动约束。
3. **客户端与服务端 token 数不同：**保留最初 127／128 的差异证据，新增显式计数口径，不直接改写统计结果。
4. **矩阵超时配置未继承：**移除生成器中的固定 600 秒，继承用户配置，并添加 600／900 秒回归。
5. **监控与正常停机竞争：**修正本次实验守护在容器退出时的状态判断；运行中无法可靠检查资源仍按保护策略停止本次实验。

其中服务启动和资源守护属于实测配套，不代表客户端会自动部署、调度或管理用户的模型服务。

## 六、建议的后续工作

1. 若 exporter 能提供逐样本源时间戳，再核验真实样本的新鲜度；否则继续标记未知。
2. 在更稳定的资源窗口做客户端 CPU 配额回切；需扩大遥测采集范围时再重复开关对照。
3. 对同一份 HTTP/SSE 轨迹核对时间边界，进一步解释 AIPerf 与 EvalScope 的延迟偏移。
4. 补齐可获得的环境身份，明确可以公开发布的支持矩阵与结果边界。
5. 经确认后再公开或迁入 HYGON-AI，并作为 hcu-bench 的可选后端接入；保留 EvalScope 交叉验证路径。

公开前应检查凭据、内网地址、私有路径和运行数据，保留上游许可及来源声明。原始压测工件可能包含请求和响应，不能默认作为公开数据上传。

## 七、与其他性能工具的差异及选型建议

### 1. 核心结论：目前没有证明必须替换 EvalScope

对于固定输入输出长度、并发 1／4／8、查看吞吐和延迟分位数等日常任务，AIPerf 与 EvalScope 的能力存在较大重叠。**换用 AIPerf 不意味着模型更快，也不天然意味着测量更准确。**

EvalScope 本身包含模型能力评测和性能压测，不能把它描述成简单的单进程发请求脚本，也不能把流量回放、延迟分位数等能力当成 AIPerf 独有功能。参见 [EvalScope 官方仓库](https://github.com/modelscope/evalscope)。

本次并发 8 的输出吞吐分别约为 214.19 和 213.24 token/s，只说明两个客户端在当前服务上的吞吐观测接近，不构成替换工具的理由；TTFT 差异尚未完全解释，也不能据此判断谁更准确。

### 2. 与不同类型工具的比较

| 对比对象 | AIPerf 的差异或价值 | 不能据此得出的结论 |
|---|---|---|
| 自写脚本、通用 HTTP 压测工具 | 已提供面向模型服务的流式处理、token 指标、负载配置及结果导出，减少自行实现和校验这些逻辑的工作 | 通用工具不能扩展，或所有自写脚本都不准确 |
| GenAI-Perf | 从依赖 Perf Analyzer 的方式转向独立多进程架构，负载执行与结果处理分离 | 换工具后一定更快；旧参数和统计口径可以不核对就迁移 |
| EvalScope | 可作为聚焦推理服务性能的另一套独立测量实现，用于相互核对；高负载扩展能力值得专项比较 | EvalScope 没有复杂流量、并行能力或尾延迟统计；AIPerf 全面更优 |
| 算子或设备 profiler | AIPerf 主要从服务接口观测用户延迟和容量，profiler 用于进一步定位底层执行瓶颈 | 服务压测结果能直接说明某个算子、内核或通信环节就是根因 |

AIPerf 的架构将控制、请求执行和分析分离，通过多进程与消息通信组织工作。这是明确的设计差异，有助于降低客户端负载生成与结果计算互相干扰的风险，但不是已经证明的性能领先。参见 [官方架构说明](https://docs.nvidia.com/aiperf/latest/architecture-internals/architecture-of-ai-perf) 和 [GenAI-Perf 迁移说明](https://docs.nvidia.com/aiperf/latest/getting-started/migrating-from-gen-ai-perf)。

### 3. 哪些差异已经验证，哪些仍是潜力

| 维度 | 潜在收益或当前增量 | 本项目证据状态 |
|---|---|---|
| 高负载请求生成 | 客户端在较高并发或请求率下仍能按计划发出负载 | **未证明优势**：当前最多并发 8，不足以评估高负载扩展性 |
| 复杂负载实验 | 固定、变长及不同到达模式采用统一实验入口 | **部分实测**：固定和 Poisson 场景已运行；不是独占能力，且目标速率未必实际达到 |
| 独立交叉验证 | 发现两套实现间的计数、计时和预热边界差异 | **已有价值**：已发现 token 计数与延迟偏移，但时间差异仍待校准 |
| 海光硬件关联 | 将服务性能与明确物理设备的功耗、温度、显存、利用率关联 | **单卡已实测**：同轮报告含四项指标；不是单请求能耗测量 |
| 实验可追溯 | 固定版本、原始工件、哈希核验、失败保留、比较条件检查 | **已实现并验证**：属于本适配层的工程增量，也可以建设在 EvalScope 外层 |
| 使用与维护成本 | 提供中文入口、本地 tokenizer 和已验证配置 | **已交付**：便利性不等于测量算法或性能领先 |

### 4. 海光二开的价值与当前缺口

基本 HTTP 压测路径通常不需要客户端直接调用海光驱动。只要服务实现兼容接口，原版客户端就可能访问。因此，本项目不是“让原本不能压测的海光卡突然能够压测”。

当前二开的主要价值是：

- **降低使用成本：**独立环境、固定依赖、本地 tokenizer、中文配置与已验证的启动说明。
- **限制误用结果：**明确计数口径，记录环境与设备身份，保留失败，阻止条件不一致时直接计算提升率。
- **补齐海光设备关联：**通过 hcu-exporter 把服务性能与对应物理卡的状态放在同一次实验中，已在 BW1100 单卡上验证。

更准确的定位是 **“AIPerf 的海光实验管理与验证适配层”**，而不是能力全面领先现有工具的新压测引擎。当前仅验证一个模型和单卡组合，跨工具延迟校准尚未收尾，尚不足以替换现有成熟流程。

### 5. 后续如何验证是否值得作为主力工具

建议保留现有 EvalScope 路径，先将 AIPerf 作为可选后端和交叉验证工具，而不是另建一套大型平台。

后续另行获得资源授权后，应围绕现有压测流程真正吃力或结果存疑的场景做同条件对照：固定服务、请求集合、缓存策略、客户端 CPU／内存及网络条件，并记录预热交接和计时边界的区别。

| 核查项 | 应记录的证据 | 判断目的 |
|---|---|---|
| 负载能否发足 | 目标与实际请求到达率、派发时间偏差、实际在途数 | 区分客户端不足与服务端背压／并发上限，不能只看最终吞吐 |
| 客户端成本 | CPU、内存、网络使用与进程配置 | 判断同样负载是否需要更多客户端资源 |
| 测量一致性 | 相同流式轨迹的事件时间及统计定义 | 解释延迟差异，而不是选更好看的数字 |
| 可重复性 | 多轮实验及交替顺序／资源回切对照 | 区分真实差异与热状态、共享资源和运行顺序影响 |
| 运行可靠性 | 成功率、错误、超时、丢失记录及不完整工件 | 不用更少成功请求或漏报错误换取表面提速 |

若没有体现出明确优势，保留为可选后端即可；若在实际高负载场景下能更稳定地发足请求、结果可解释且维护成本可接受，再考虑扩大使用。上述是待执行的选型验证，不代表已经完成的新实验。

**结论：目前已有工程适配和独立验证价值，但尚未证明替代 EvalScope 的性能优势。项目是否继续扩大，应由真实需求与对照结果决定，而不是为了增加仓库而增加工具。**

## 八、总结

目前已完成的是：**海光环境可运行的压测入口、固定版本与离线 tokenizer 适配、显式 token 计数、遥测适配代码、中文可追溯报告，以及单卡实机与跨工具验证。**

当前阶段可概括为：**软件首版、单卡压测和同轮硬件监控已实测；跨工具延迟差异和遥测样本新鲜度仍未解决，不作为性能认证或自动放行依据。**
